# Switchboards

`switchboards/<name>.yaml` (the name must keep `ebwes-<name>` within 15
characters):

| Key | Meaning |
|---|---|
| `about` | one line for `burger list` |
| `route` | `waterway`, `soap` or `site`: the topology the items run on |
| `apps.prs` | sceptre-phenix-apps PRs merged in order; `sync` fails and names the files when one conflicts with those before it. Integers only |
| `apps.branch` | instead of `prs`: use this branch as the apps tree, with no merges. `remote: fork` (default; the `gh` user's fork, from `gh api user`) or `upstream`. `contains: [159, 161]` lists the PRs the branch holds, in merge order; items' `requires.apps_prs` are checked against it, and `burger prs` shows the board as carrying them. `sync` fetches the branch into `refs/burger/branch/<remote>/<branch>` and records its sha in the manifest. `burger prs` marks the board stale when the branch has a new head since sync; it cannot tell whether the branch still holds its PRs' current heads, so rebuild it when a PR moves |
| `bennu` | the bennu tree to build: `pr: N` (one PR), `prs: [84, 85]` (several PRs merged in order over upstream `main`, like `apps.prs`; `sync` fails and names the files when one conflicts), or `branch` (with `remote`) as for apps; plus `install`, `pip`, `pip_env` |
| `phenix` | run the board on a proposed sceptre-phenix, as `minimega` does: `pr: N` (a sandialabs/sceptre-phenix PR) or `branch` with `remote`. `build` makes `burger/phenix:<sha12>-<minimega hash>` from that checkout's `docker/Dockerfile`, `install` swaps it into the compose `phenix` service first, then installs the apps and the board's minimega, `down` puts stock back. `--phenix` on `run` or `sync` does the same for any board, see the [run book](run-book.md#run-a-board-on-a-phenix-pr-or-branch) |
| `minimega` | run the board on a proposed minimega instead of the stock container: `pr: N` (a sandia-minimega/minimega PR) or `branch` with `remote: fork` (default) or `upstream`. `build` makes the image `burger/minimega:<sha12>` from that checkout's `docker/Dockerfile`, `install` swaps it into the compose `minimega` service and installs its `minimega.py` into phēnix, `down` puts stock back. `--minimega` on `run` or `sync` does the same for any board, see the [run book](run-book.md#run-a-board-on-a-minimega-pr-or-branch) |
| `probes` | host-side checks `verify` runs while the experiment is up, a list of names from `src/burger/probes/` (`mm-bindings`: minimega's python bindings from the phēnix container; `mm-capture`: its capture engine; `workflow-vars`: phēnix PR 576's `${NAME}` variables, needs `phenix:`); an unknown name is an error at load, a probe on a board whose experiment is down gives a `skipped` row. `burger probe <board> [name ...]` runs them on their own |
| `services` | `[name, ...]`: `up` runs `scripts/<name>.sh start` and `down` runs `scripts/<name>.sh stop` on the host, for a service the board needs (the groundtruth boards' Elasticsearch container, `groundtruth-es`). A board left up after a failed run keeps its service until `burger down` |
| `items` | `<item>: on` switches an item on (`apps/x`, `bennu/x` for the other kinds) |
| `overrides` | per-item changes to `config` or `verify` |
| `linux_only` | same as `--linux-only` |
| `fdlogs` | field-device log knobs, see [verify](verify.md#field-device-logs): `fail_on` (`crash`, `error` or `none`; default `crash` when the board installs a bennu deb from a PR or branch, else `none`), `flood_bytes_per_min` (50000000), `repeat` (5000) |
| `runs` | explicit run layout; by default burger builds `health` plus one run per item from the item's `stages` |

A component whose `start` polls until phēnix stops it (hoststats) needs
`background: true` in its item file and a stop entry in the run, or `start`
never returns and the run hangs; `check` refuses a switchboard that breaks
this.
